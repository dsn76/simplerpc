**simplerpc** is a lightweight, high-performance framework for inter-process remote procedure calls (RPC) in Linux, written in C.

The project provides mechanisms for transparent inter-process communication (IPC) using shared memory and UNIX sockets, and includes its own lock-free primitives (MPMC queues, a function registry) and a transactional shared-memory allocator.

## Demo
Terminal one: `./log` (multiple instances may be started). Terminal two: `./clc` (same). Terminal three: `./app`. In the first terminal's output you will see `LOG("Hello, world, from app! my pid=...")`. The calls `log_write("Hello")` and `calc_add(1, 2)` in `app` are ordinary C functions, but they execute in the `log` and `clc` processes. All argument serialization is hidden inside X-macros — there is nothing to do by hand. To use it in your own application: include `#include "libsrpc.h"` in your sources, declare the prototypes of the functions you export in `./src/libsrpc_rpc_functions.h` (this is part of the library's own sources, not a separate public API header), rebuild `libsrpc.so` and link it into your application with the `-Wl,--no-as-needed` flag. More details — in `./example`.

## Overview
The **simplerpc** project (the `libsrpc` library) is a high-performance framework for organizing remote procedure calls (RPC) between different processes in a Linux environment.
The architecture is based on shared memory for data transfer and UNIX sockets for signaling and for handing out the memory descriptor. Memory management inside the shared segments is done by the transactional **TLSF** allocator (`tlsf_txn` v4.1), whose sources are included in the project tree (`libs/tlsf_txn/`). Synchronization between threads and processes is built on POSIX semaphores placed in shared memory (`pshared`) and on lock-free structures: MPMC queues (Multi-Producer Multi-Consumer) and a function registry with CAS publication.

The project's distinguishing feature is the **absence of an IDL and a code generator**: the role of a process (caller or executor) is determined at link time via `__attribute__((weak, alias))`, and all argument serialization is generated by the preprocessor from a single X-macro, `RPC_LIST`. The second feature is a built-in static loader (embedded loader), embedded in the `libsrpc.so` dynamic library as a C array using the `xxd` utility, which lets the library start its background coordinator process (the daemon) directly from memory, without any file on disk.


## 📋 Main Features

- **Inter-process RPC:** Transparent calls to functions implemented in one process, issued from another process's address space.
- **Shared Memory:** A common memory region mapped by all processes at the same virtual address is used for data exchange without redundant copies.
- **Transactional TLSF allocator:** The `tlsf_txn` allocator with deterministic O(1) allocation, a robust mutex, and a BUL (Binary Undo Log) rollback journal: a process crash in the middle of an operation does not corrupt the pool.
- **Memory ownership model:** Every block in the pool is tagged with the UID of its owner process (up to 12 owners per block). When a process disconnects, the daemon automatically frees all of its blocks.
- **Garbage collector:** A background GC thread in the daemon reclaims service blocks marked for deferred cleanup, checking their occupancy via Hazard Pointers.
- **Dynamic linking of RPC functions:** A process sends the daemon a bitmap of the functions it can execute; the daemon registers it in a lock-free registry in shared memory.
- **Multicast:** A single call can be executed by all registered processes (`RPC_SEND_ALL`) or by the first one only (`RPC_SEND_FIRST`); the results are collected via `libsrpc_lastreq_num()` / `libsrpc_lastreq_get()`.
- **Synchronization and queues:** A lock-free MPMC queue per process and POSIX semaphores in shared memory for sleeping/waking executor threads.
- **Embedded Loader:** A statically compiled loader inside the library starts the daemon from a `memfd` via `fexecve()` — no file on disk.
- **Optional allocator substitution:** Interception of `malloc`/`calloc`/`realloc`/`free` with an "on-the-fly" switch to the shared-memory pool (disabled by default, see `DISABLE_ALLOC`).

## 🛠 Technology Stack

- **Programming language:** C17
- **Build system:** CMake (version 3.10+), Make
- **OS:** Linux (x86_64; uses `memfd_create`, `fexecve`, abstract UNIX sockets, `MAP_FIXED_NOREPLACE`, `MADV_DONTFORK`)
- **Dependencies:**
  - Standard libraries: `pthread` (threads, semaphores), `dl` (dynamic loading).
  - The `xxd` utility — at build time, for embedding the loader.
  - No external dependencies and no git submodules: the `tlsf_txn` allocator is included in the project tree.

## 🚀 Build and Installation

The project has no submodules; a plain clone is enough.

### 1. Clone the Repository
```bash
git clone https://github.com/dsn76/simplerpc.git
cd simplerpc
```

### 2. Build the Project
The project ships a `Makefile` that automates the CMake invocation.

```bash
make all
```
*This command creates the `build` directory, configures the project with CMake, and compiles the static allocator library `libtlsf.a`, the dynamic library `libsrpc.so`, the examples, and the benchmarks.*

For a manual build with CMake:
```bash
mkdir -p build && cd build
cmake ..
make
```

Clean: `make clean` (removes the `build` directory).

### Build Modes and Parameters

The build mode is set by the `BUILD_TYPE` variable:
- `release` (default): `-O3` optimization.
- `debug`: debug information `-O0 -ggdb3 -DDEBUG` (enables the verbose `DBG_PRINT` output).

The following additional CMake parameters are supported:

| Parameter | Default | Purpose |
|---|---|---|
| `BUILD_TYPE` | `release` | Build mode: `debug` / `release` |
| `ENABLE_SANITIZER` | `OFF` | AddressSanitizer + UndefinedBehaviorSanitizer (`debug` only) |
| `DISABLE_ALLOC` | `ON` | Disables substituting the standard `malloc`/`calloc`/`realloc`/`free` with the shared-memory allocator |
| `DBG_LVL` | `2` | Message level: `0` — off, `1` — ERR, `2` — ERR+WRN, `3` — ERR+WRN+INF |
| `MPMCQ_DEGREE` | `10` | MPMC queue capacity as a power of two (`2^10 = 1024`) |
| `SHMEM_SIZE_KB` | `4096` | Shared-memory size in kilobytes |
| `SHMEM_BASE_VADR` | `0x200000000000` | Base virtual address for the shared-memory mapping |

Example:
```bash
cmake -DBUILD_TYPE=debug -DDBG_LVL=3 -DSHMEM_SIZE_KB=16384 ..
```

> **Important:** on every CMake configuration a `BUILD_TS` stamp is generated, from which the daemon name, the abstract socket name, and the shared-memory signature are formed. Applications built with different builds of `libsrpc.so` **will not** interact with each other — this protects against `RPC_LIST` version mismatches. After rebuilding the library, all participating processes must be restarted.

## 💡 Usage Example

### Declaring an RPC Function

All functions available for remote calls are listed in a single X-macro, `src/libsrpc_rpc_functions.h`:

```c
#define RPC_LIST    \
    XF(RPC_SEND_ALL, int,   testlocal) \
    XF(RPC_SEND_ALL, pid_t, log_write, const char*) \
    XF(RPC_SEND_ALL, int,   calc_add, int, int) \
    XF(RPC_SEND_ALL, void,  all_exit) \
```

Format: `XF(dispatch policy, return type, name, parameter types...)`. Functions with a variable number of parameters are not allowed.

### Who Is the Executor and Who Is the Caller

There is no separate "server" API. A process that **defines** a function from `RPC_LIST` in its own code automatically becomes its **executor** — the strong symbol overrides the weak alias from `libsrpc.so`. A process that does not define the function gets a stub on the call and sends an RPC request:

```c
/* Executor process: defines the function — and becomes its server. */
pid_t log_write(const char* msg) {
    fprintf(stderr, "LOG: '%s'\n", msg);
    return getpid();
}
```

```c
/* Caller process: simply calls, defining nothing. */
char *str = libsrpc_shmem_malloc(1024);
snprintf(str, 1024, "Hello from pid=%d", getpid());

pid_t pid = log_write(str);          /* goes via RPC to all executors */

/* Collecting the results from all executors (RPC_SEND_ALL): */
for (int i = 0, num = libsrpc_lastreq_num(); i < num; i++) {
    int rc = libsrpc_lastreq_get(i, &pid, sizeof(pid));
    if (!rc) printf("pid[%d]=%d\n", i, pid);
}
libsrpc_shmem_free(str);
```

> Pointers passed to RPC functions must address the shared pool (`libsrpc_shmem_malloc`) — the library copies only the arguments themselves, not the data behind the pointers.

> When linking an application that **only** exports RPC functions, the `-Wl,--no-as-needed` flag is mandatory: without references to `libsrpc.so` symbols the linker drops the `DT_NEEDED`, and the library's constructor will not run.

### Running the Examples

The `example/` directory contains four applications. The background coordinator daemon does not need to be started — it is brought up automatically by the first process linked against `libsrpc.so`, and it exits after the last client disconnects.

1. **`log`** — executor process, provides `log_write()`.
2. **`clc`** — executor process for `calc_add()`, which itself calls `log_write()` via RPC.
3. **`app`** — calling process: allocates a string in the shared pool, calls `log_write()` and `calc_add()`, prints the results.
4. **`all_exit`** — calls `all_exit()`, stopping all executors in a broadcast.

**Starting the executors (in separate terminals):**
```bash
./build/example/log
./build/example/clc
```

**Starting the client:**
```bash
./build/example/app
```

**Stopping the executors:**
```bash
./build/example/all_exit
```

During the run, the client allocates memory in the shared pool (`libsrpc_shmem_malloc`), writes a string there, and initiates an RPC call to the logging function, which executes in the `log` process. The `calc_add()` function, in turn, executes in the `clc` process.

## 📈 Performance Measurements

The `bench/` directory contains measurements of the RPC call latency compared with baseline IPC mechanisms:

```bash
make all
./bench/run_bench.sh build 4000
```

The script starts an executor process, runs the baselines (`pipe`, `socketpair`), then a single-threaded and a multi-threaded round-trip RPC, and prints the latency distribution (min/p50/p90/p99/max) and the throughput.
