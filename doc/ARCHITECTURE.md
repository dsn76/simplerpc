# Архитектура SimpleRPC

Документ описывает внутреннее устройство `libsrpc`: из каких частей состоит библиотека, как проходит вызов, что происходит при падении процессов и где у текущей реализации слабые места. Пользовательская сторона — сборка, API, примеры — описана в [README](../README.md).

## 🏗 Общая концепция

**simplerpc** — RPC поверх разделяемой памяти. Классические RPC-системы сериализуют вызов в поток байтов (Protobuf, JSON) и гонят его через сокет. `simplerpc` кладёт аргументы в общий пул, который все процессы отображают по одному и тому же виртуальному адресу. Указатель, полученный в одном процессе, валиден в другом, а сокет нужен только для служебных сообщений.

### Ключевые принципы

1. **Zero-Conf Daemon.** Фоновый процесс-координатор поднимается сам при загрузке библиотеки первым процессом и завершается после отключения последнего клиента. Конфигурации, PID-файлов и сервисов нет.
2. **Memory-Centric.** Дескрипторы процессов, реестр функций, очереди, запросы и ответы лежат в разделяемом пуле под управлением транзакционного аллокатора TLSF. Через сокет данные вызова не идут.
3. **Link-Time Dispatch.** Роль процесса для каждой функции выбирает линковщик через `weak alias`: определил функцию — исполнитель, не определил — вызывающий. IDL и генератора кода нет, всё раскрывается препроцессором из одного X-макроса.
4. **Ownership-Based Cleanup.** Каждый блок пула помечен UID процессов-владельцев. За умершим процессом убирают по этому UID, без отдельного реестра аллокаций. Живой запрос может отложить уборку пользовательских блоков конкретного процесса, удерживая его UID.
5. **Transparent IPC (опционально).** Подмена `malloc`/`free` позволяет существующему коду работать с пулом без изменений. По умолчанию выключена (`DISABLE_ALLOC=ON`).

## 🧩 Компоненты

### 1. Демон-координатор (Guard Daemon)

Демон владеет пулом, реестром функций и дескрипторами процессов. RPC-трафик через него не идёт: демон только раздаёт память, регистрирует исполнителей и убирает за умершими.

* **Запуск.** `spawn_daemon()` делает двойной `fork()` с `setsid()` между ними. Первый потомок сразу завершается, и родитель забирает его через `waitpid()`. Второй становится сиротой без управляющего терминала и не оставляет зомби.
* **Встроенный загрузчик.** Исполняемый файл демона на диске не лежит. При сборке `src/libsrpc_loader.c` компилируется `gcc` в небольшой динамически слинкованный ELF без символов. `xxd -i -n loader` превращает его в C-массив, и массив вкомпилируется в `libsrpc.so`. При запуске массив пишется в `memfd` и исполняется через `fexecve()`. В `argv[0]` передаётся имя демона `"simplerpc_" BUILD_TS`. Окружение состоит из одной переменной `LIBSIMPLERPC_SO` с путём к библиотеке, полученным через `dladdr()`. Загрузчик делает `dlopen()` этой библиотеки и передаёт управление в `simplerpc_daemon_main()`.
* **Почему процесс, а не поток.** Демону нужно чистое адресное пространство: он отображает пул по фиксированному адресу `SHMEM_BASE_VADR` и не должен тащить за собой аллокации, потоки и дескрипторы приложения, которое его породило. Кроме того, его жизнь не должна зависеть от жизни этого приложения.
* **Выбор лидера.** Демона пытается поднять каждый процесс, но `bind()` абстрактного сокета атомарен. Проигравшие получают `EADDRINUSE` и молча завершаются. Клиент повторяет `connect()` при `ECONNREFUSED` до 10 000 раз с паузой 100 мкс, то есть около секунды.
* **Обязанности.** Слушать абстрактный сокет, создать пул и раздать его дескриптор, вести реестр функций, запустить поток сборщика мусора, убирать за отключившимися клиентами.
* **Завершение.** Главный цикл — `epoll_wait()` с таймаутом 1 с. Когда счётчик клиентов падает до нуля, демон выходит, и анонимный `memfd` пула исчезает вместе с последней ссылкой.
* **Вывод.** `stdout` и `stderr` демон наследует от процесса, который его поднял, поэтому сообщения демона появляются в терминале этого процесса.

### 2. Транспорт (UNIX-сокет и SCM_RIGHTS)

Сокет служит только для подключения, регистрации функций, передачи дескриптора пула и обнаружения смерти клиента.

* **Абстрактный сокет.** Имя — `"simplerpc_" BUILD_TS`, где `BUILD_TS` — метка времени конфигурации сборки. Процессы с разными сборками `libsrpc.so` попадают в разные, непересекающиеся «домены». У абстрактного сокета нет прав файловой системы.
* **Порядок подключения** (`libsrpc_unix_server_addclient`): `accept4()` → `SO_PEERCRED` (из учётных данных берётся только PID) → `libsrpc_proc_create(pid)` → `SO_RCVTIMEO = 5 с` → чтение регистрационного сообщения → регистрация функций → передача FD пула → постановка в `epoll`. Клиент с неверной сигнатурой до пула не допускается. UID клиента не проверяется.
* **Отображение пула.** Получив FD, клиент делает `mmap()` с `MAP_FIXED_NOREPLACE` по адресу `SHMEM_BASE_VADR` и сверяет сигнатуру в заголовке пула. Если адрес занят, `mmap()` завершается ошибкой, а не перезаписывает чужое отображение.
* **Детектор смерти.** Обрыв соединения (`EPOLLHUP | EPOLLRDHUP` или `recv() == 0`) — единственный и достаточный признак того, что клиента больше нет. Сокет закрывает ядро, поэтому событие приходит при `exit()`, `SIGKILL` и segfault одинаково. Heartbeat и таймауты для этого не нужны.
* **Управляющий поток клиента.** В приложении соединение обслуживает detached-поток `unix_client`. Он подключается, отправляет регистрацию, получает FD, отображает пул, находит свой дескриптор процесса, запускает потоки-исполнители, выставляет статус `RUN` и разрешает RPC (`rpc_enable`). Конструктор библиотеки ждёт на семафоре, пока поток не закончит инициализацию или не сообщит об ошибке, поэтому к входу в `main()` процесс уже готов. Дальше поток спит в `epoll_wait()`. Для выхода его будят через `eventfd`.

### 3. Управление памятью (TLSF в разделяемой памяти)

* **tlsf_txn v4.1.** Транзакционный TLSF-аллокатор, исходники лежат в дереве проекта (`libs/tlsf_txn/`). Выделение за O(1) благодаря матрице свободных списков `FL × SL` и битовым картам. Формат пула версионирован (`TLSF_FORMAT_VERSION = 0x00040000`), чужой формат отвергается.
* **Robust-мьютекс внутри пула.** Межпроцессное исключение даёт `pthread_mutex_t` с атрибутами `PTHREAD_PROCESS_SHARED | PTHREAD_MUTEX_ROBUST | PTHREAD_MUTEX_RECURSIVE`, размещённый в управляющей структуре пула. `libsrpc` сам его не берёт и вызывает только `tlsf_*`. Исключение — сборщик мусора, который освобождает пачку блоков под одним явным `tlsf_lock()`.
* **BUL (Binary Undo Log).** Перед каждой записью 8-байтового слова метаданных старое значение кладётся в стек отката внутри пула, успешная операция сбрасывает стек (коммит). Если владелец мьютекса умер, следующий захват получает `EOWNERDEAD`, откатывает незавершённую операцию и вызывает `pthread_mutex_consistent()`. Пул остаётся согласованным без внешнего сторожа. Откатываются только метаданные аллокатора: данные внутри блоков журнал не защищает.
* **Владельцы (UID).** В заголовке блока массив `uid[12]`. Блок возвращается в пул, только когда из массива вычеркнуты все владельцы. `libsrpc` передаёт в аллокатор `proc_uid` — 16-битный идентификатор, который демон выдаёт каждому клиенту (у самого демона `DAEMON_PROC_UID = 1`). Идентификаторы переиспользуются после отключения процессов.
  * `libsrpc_shmem_link()` добавляет владельца.
  * `libsrpc_shmem_free()` вычёркивает только UID вызывающего.
  * `libsrpc_shmem_realloc()` работает только для блока с единственным владельцем.
  * `libsrpc_shmem_get_size()` читает размер полезной нагрузки.
* **Типы блоков.** 15-битное поле `data_type` в заголовке хранит тип `libsrpc_shm_data_type_t`: `USER` (данные приложения), `PROC` (дескриптор процесса), `REGFN` (блок реестра функций), `REQUEST` (блок запроса). По нему деструкторы и сборщик мусора отличают пользовательскую память от служебной.
* **Флаг отложенной очистки (`dc`).** Один бит в том же слове. Метка «блок логически мёртв, но освобождать его сейчас нельзя». Ставится через `libsrpc_shmem_free_dc()` (= `tlsf_setdc()`), читается сборщиком мусора.
* **Коды ошибок.** Функции памяти пишут в код ошибки потока (`libsrpc_errno_get()`) код аллокатора `TLSF_ERR_*` (1…15). Эти номера пересекаются с системными `errno`, поэтому их расшифровывает `tlsf_strerror()`, а не `libsrpc_strerror()`.
* **Подмена аллокатора (опционально).** Библиотека может перехватывать `malloc`, `calloc`, `realloc` и `free`, получая оригиналы через `dlsym(RTLD_NEXT)`. Флаг в TLS переключает поток между системной кучей и пулом (`libsrpc_alloc_sw_std()` / `libsrpc_alloc_sw_shm()`). По умолчанию код перехвата не собирается (`DISABLE_ALLOC=ON`).

### 4. Сборщик мусора (Shared Memory GC)

Отдельный поток, живущий **только в демоне** (запускается из `libsrpc_shmem_create()`). Он освобождает служебные блоки, которые нельзя было освободить сразу, потому что их ещё могли читать потоки других процессов, и пользовательские блоки, уборка которых была отложена удержанием.

* **Будильник в пуле.** Структура GC — поток, семафор и список отложенных блоков `list_head` — лежит в `libsrpc_shmem_t`, поэтому `libsrpc_shm_gc_wakeup()` будит сборщик из любого процесса через `sem_post`. Кроме того, GC просыпается сам `SHM_GC_FREQ_CHECK` раз в секунду (по умолчанию 10).
* **Служебные блоки.** `tlsf_free_uid_blocks(pool, 0, ...)` обходит кучу и собирает выделенные блоки с `dc == 1` в локальный накопитель (до 1024 за проход). Отдельного списка у служебных блоков нет: его роль играет флаг в заголовке.
* **Проверка занятости (Hazard Pointers).** Для каждого найденного запроса `libsrpc_req_is_busy_proc()` проверяет `threads[i].hp_req` у всех живых процессов. Если хотя бы один поток-исполнитель опубликовал указатель на этот запрос, блок остаётся до следующего прохода.
* **Отложенные пользовательские блоки.** Если процесс умер, пока его UID удерживался, указатели на его пользовательские блоки попадают в узел списка `gc.list_head` вместе с UID. Узлы выделяются обычным `malloc` в адресном пространстве демона и в пул не входят. На каждом проходе GC проверяет, держит ли ещё кто-нибудь этот UID. Если нет, блоки узла освобождаются.
* **Пакетное освобождение.** Готовые к освобождению блоки удаляются одной пачкой: `tlsf_lock()`, `tlsf_free_nb()` × N, `tlsf_unlock()`. Так межпроцессный мьютекс берётся один раз на проход, а не на каждый блок.

### 5. Механизм RPC и X-макросы

Шаблонный код генерирует препроцессор (`src/macro.h`, `src/argfunc.h`).

* **RPC_LIST.** X-макрос в `src/libsrpc_rpc_functions.h` — единственный источник истины. Запись: `XF(политика рассылки, тип возврата, имя, типы параметров...)`. Из неё раскрываются прототипы, идентификаторы, обёртки, таблица функций и `switch` диспетчера.
* **Идентификаторы.** Внутри библиотеки функция получает `sRPCFNID_<name>` (нумерация после `sRPCFNID_START = 16`) и индекс в реестре `sRPC_ID2IDX(id)`. В публичном `libsrpc.h` тот же номер виден как `libsrpc_funid_<name>`.
* **Обёртки.** Для каждой функции генерируется заглушка `librpcimp_<name>` (`sRPCFN(name)`). Она сериализует аргументы в блок запроса `libsrpc_request_t`, рассылает его по очередям исполнителей, ждёт ответов и возвращает результат первого слота.
* **Диспетчеризация.** В исполнителе макросы `M_DECL`, `M_EXTRACT`, `M_ARGNAMES` раскладывают буфер обратно по переменным стека, вызывают настоящую функцию и пишут результат в слот ответа. Для `void`-функций слот получает флаг готовности без данных.
* **Ветвление по типу возврата.** Препроцессор C не умеет сравнивать типы, поэтому используется макрос `COMPARE_void`, определённый только для `void`. `IIF(EQUAL(rettype, void))` раскрывается в разный код для `void`- и не-`void`-функций (`RETDATA`).
* **Ограничения по построению.** Функции с переменным числом аргументов недопустимы. Аргументы копируются побайтово (`memcpy`), поэтому передаются скалярные типы и указатели, причём указатель осмыслен, только если адресует общий пул.

### 6. Регистрация функций

Регистрация «кто что умеет исполнять» проходит четыре стадии и не требует ни `dlsym`, ни генерации заглушек в рантайме.

1. **Weak alias (линковка).** Для каждой функции из `RPC_LIST` библиотека объявляет `__attribute__((weak, alias("librpcimp_" #name))) rettype name(...);`. Если приложение определило функцию, сильный символ перекрывает alias, и процесс становится **исполнителем**. Если нет, символ разрешается в заглушку, и процесс становится **вызывающим**. Решение принимается для каждой функции отдельно.
2. **Битовая карта (старт процесса).** Таблица `srpc_fn[]` хранит для каждой функции пару адресов: `.rpc` (заглушка) и `.loc` (куда реально разрешился символ). `libsrpc_bmp_func_set()` сравнивает их и ставит бит «умею исполнять» в `srpc_bmp_func_t`. Это сравнение двух указателей, без строк и поиска символов.
3. **Передача демону (подключение).** Карта уходит демону в сообщении `regfn_msg_t { size, sign[32], bmp }` сразу после `connect()`, до получения FD пула. Демон проверяет размер и сигнатуру `"simplerpc_" BUILD_TS`: это защита от стыковки процессов с разными `RPC_LIST`.
4. **Запись в реестр (демон).** `libsrpc_reg_func_form_bmp()` вставляет указатель на `libsrpc_proc_t` клиента в реестр `srpc_regfn_shm_t` в пуле. Клиенты в реестр не пишут никогда.

**Устройство реестра** (по одной записи на функцию):

* `main_block` — 8 слотов `_Atomic(libsrpc_proc_t *)` прямо в структуре. Типичный случай, единицы исполнителей на функцию, обходится без выделения памяти.
* `ext_block` — при переполнении главного блока выделяется расширение на 32 слота больше прежнего, старое содержимое копируется, новый блок публикуется через CAS. Писатель у реестра один — главный поток демона, CAS страхует публикацию.
* Старый `ext_block` сразу не освобождается: его сигнатура гасится, блок помечается `dc`, и будится GC. Получается RCU-подобная отложенная реклаймация, потому что читатели в других процессах могут ещё обходить старый блок.
* `num_all` — атомарный счётчик исполнителей функции. Вызывающий читает его, чтобы зарезервировать слоты ответов. Снаружи то же значение отдаёт `libsrpc_fnreg_num_get()`. При `num_all == 0` вызов сразу завершается с `ENOREGFUN`.
* Вставка и удаление слотов делаются CAS-операциями, без мьютексов.

**Дерегистрация** происходит при закрытии сокета: `libsrpc_proc_destroy()` → `libsrpc_unreg_func_proc()` снимает процесс из всех блоков реестра и уменьшает `num_all`.

**Замечание по линковке.** Приложение, которое только исполняет функции, может не ссылаться ни на один символ `libsrpc.so`. С флагом линковщика `--as-needed` зависимость `DT_NEEDED` будет выброшена, конструктор библиотеки не выполнится, и процесс не подключится к пулу. Поэтому в `example/` и `bench/` используется `-Wl,--no-as-needed`.

### 7. Дескрипторы процессов и потоков

Структура `libsrpc_proc_t` создаётся демоном в пуле для каждого подключившегося клиента (тип блока `PROC`). Это точка входа для всех адресованных ему запросов.

* **Сигнатура и статус.** `sign` (`LIBSRPC_PROC_SIGN`) и `status` атомарны. `libsrpc_proc_is_valid()` требует верной сигнатуры и статуса `RUN`, поэтому инвалидация процесса видна остальным сразу и без блокировок.
* **`proc_uid`.** 16-битный идентификатор от демона, он же UID владельца в аллокаторе.
* **Очередь и семафор.** У процесса одна MPMC-очередь входящих запросов и один семафор пробуждения `sem_wakeup` на все его потоки-исполнители.
* **Потоки-исполнители.** Массив `threads[]` лежит в том же блоке, его размер — число онлайн-CPU (`sysconf(_SC_NPROCESSORS_ONLN)`). Потоки запускаются по маске `sched_getaffinity`, по одному на доступное ядро, и привязываются к нему (`pthread_start_all_cpu`). Потоки получает **каждый** процесс, загрузивший библиотеку, включая чисто вызывающие. Элемент массива хранит `hp_req` — Hazard Pointer на обрабатываемый запрос.
* **Список запросов.** `req_head` — список всех блоков запросов процесса. По нему сборщик мусора ищет занятые запросы, а уборка процесса проверяет удержания UID.

### 8. Синхронизация и очереди

Собственные фьютексы (`libsrpc_futex.*`) из версии 0.1.x удалены, синхронизация построена на POSIX-примитивах в пуле.

* **MPMC-очередь.** `lf_mpmc_queue` — lock-free очередь по схеме Вьюкова (массив ячеек со счётчиком `seq`) внутри `libsrpc_proc_t`. Ячейки выровнены на кэш-линию (`alignas(64)`), `head` и `tail` разнесены по разным линиям. Ёмкость — степень двойки, задаётся при сборке (`MPMCQ_DEGREE`, по умолчанию `2^10 = 1024`). В ячейке лежит только указатель на запрос, а свой слот ответа исполнитель находит по `resp->hp_proc`.
* **Постановка в очередь.** Если очередь полна, вызывающий повторяет попытку: 16 раундов по 32 попытки с инструкцией `pause`, между раундами `sched_yield()`. Если места так и не нашлось, слот ответа получает `-ENOMEM`, и запрос этому исполнителю не отправляется.
* **Ожидание исполнителей.** Опустошив очередь, поток-исполнитель не засыпает сразу: около 1024 итераций он активно проверяет очередь с паузами (`DEQUEUE_RETRY`, `libsrpc_cpu_pause(32)`). Только после этого он отмечается в `threads_wait`, ещё раз проверяет очередь и засыпает на `sem_wakeup`. Короткое активное ожидание экономит пробуждение при плотном потоке запросов, но стоит процессорного времени после каждого запроса.
* **Пробуждение.** Вызывающий делает `sem_post` на семафоре процесса, только если там есть спящие потоки (`threads_wait > 0`). Семафоры `sem_t` созданы с `pshared = 1` и обёрнуты тонким слоем `libsrpc_sem_*` (`libsrpc_wrapper.h`).
* **Семафор в запросе.** У каждого `libsrpc_request_t` свой `sem_wakeup`: по нему исполнитель будит вызывающий поток, когда ответ готов.
* **Список со спинлоком.** `libsrpc_list_spin` — односвязный список. Запись идёт под `pthread_spinlock_t`, обход — без блокировок, через атомарные загрузки с `acquire`. Используется для списка процессов, списка запросов и списка отложенных блоков GC.
* **Пул блоков фиксированного размера.** `libsrpc_fixblockalloc` — пул на FIFO-кольце индексов с доращиванием (`nextpool`). Демон хранит в нём дескрипторы клиентских соединений, в **локальной** памяти. Синхронизации в пуле нет: к нему обращается только главный цикл `epoll` демона.

### 9. Запрос и ответ

Один блок пула содержит и запрос, и все ответы на него, поэтому память под ответы отдельно не выделяется.

```text
libsrpc_request_t
+----------------------------------------------------------------------+
| node | sem_wakeup | hp_regfn | sign | seq_num | funid | bufsz |      |
| retoff | retsz | retnum | gc_lock_uid |                              |
+----------------------------------------------------------------------+
| buf[]:                                                               |
|   [аргументы .......]  <- retoff = ALIGNLONG(len(args))               |
|   [libsrpc_response_t #0][ret]  <- retsz каждый                       |
|   [libsrpc_response_t #1][ret]                                        |
|   ...                          <- retnum слотов                       |
+----------------------------------------------------------------------+

libsrpc_response_t: { hp_proc (от кого ждём ответ), rc, buf[] }
```

* **Кэш блока запроса.** Указатель на последний блок потока хранится в TLS (`current_req`). Если новый запрос помещается, блок переиспользуется без обращения к аллокатору. Если нет, выделяется новый с двукратным запасом. Старый блок освобождается сразу, а если в нём остался недописанный или просроченный ответ — через флаг `dc` и сборщик мусора. На горячем пути аллокатор не вызывается. Этот же указатель обслуживает `libsrpc_lastreq_num()` / `libsrpc_lastreq_get()`. Блок регистрируется как данные потока (`pthread_key_create`) и освобождается при завершении потока.
* **Удержание UID (`gc_lock_uid`).** Четыре 16-битных слота в теле запроса. `libsrpc_shmem_proc_lock(idx, ptr)` берёт исполнителя из слота ответа `idx`. Если `tlsf_check_uid()` подтверждает, что `ptr` принадлежит его `proc_uid`, UID записывается в свободный слот, и функция возвращает номер слота (`0…3`). При замене кэшированного блока маска копируется в новый, при повторном использовании не сбрасывается. Пока UID встречается хотя бы в одном запросе живого процесса, `libsrpc_proc_destroy()` не освобождает пользовательские блоки этого UID сразу. Удержание привязано к потоку: его снимает поток, который его взял, и оно пропадает вместе с потоком или процессом.
* **Протокол готовности.** Исполнитель CAS-ом ставит в `rc` флаг `LIBSRPC_RC_FLAG_LOCK` (`0xC0000000`), копирует результат и публикует `LIBSRPC_RC_FLAG_READY` (`0x80000000`). Отрицательное значение `rc` — код ошибки слота, `0` — ответа ещё нет. Обёртка принимает ответ только при точном совпадении с флагом готовности. Если слот ещё в состоянии `LOCK`, она ждёт до 100 итераций `pause`.
* **Валидация.** `libsrpc_req_is_corrupted()` проверяет сигнатуру двойным чтением с `acquire`, до и после чтения полей, и согласованность размеров. `libsrpc_req_destroy()` гасит сигнатуру через CAS, поэтому повторное уничтожение безопасно. Это защита от use-after-free при одновременной работе GC и исполнителя.
* **Политики рассылки.** Реестр обходится по порядку: сначала `main_block`, затем `ext_block`.
  * `RPC_SEND_ALL` — запрос уходит всем исполнителям (`retnum = num_all`).
  * `RPC_SEND_FIRST` — первому исполнителю, который принял запрос (`retnum = 1`).
  * `RPC_SEND_LAST` — последнему непустому слоту обхода.
  * `RPC_SEND_RR` — одному исполнителю по кругу (атомарный счётчик `req_send_rr` по модулю `num_all`).
  * У `LAST` и `RR` запасного исполнителя нет: если выбранный процесс не принял запрос, вызов завершается с `ENOTAVAILABLE`.
* **Частичная рассылка.** Если разослать удалось меньше запросов, чем резервировалось слотов, ожидаемое число ответов уменьшается. Если не удалось ни одного, вызов завершается с `ENOTAVAILABLE`.
* **Таймаут.** Вызывающий ждёт в цикле `libsrpc_sem_wait_timeout_us()` и после каждого пробуждения пересчитывает готовые слоты. Интервал задаётся в микросекундах:
  * `libsrpc_timeout_oneshot_set()` — следующий вызов потока;
  * `libsrpc_timeout_func_set()` — функция, в пределах потока;
  * `libsrpc_timeout_global_set()` — весь процесс.

  По умолчанию `LIBSRPC_TIMEOUT_DEFAULT` (1 с), нижняя граница `LIBSRPC_TIMEOUT_MINIMUM` (100 мкс). Интервал отсчитывается заново после каждого пробуждения. Если за интервал не пришло ни одного нового ответа, пустые слоты помечаются `-ERPCWAITIMEDOUT`, и ожидание заканчивается.

### 10. Рекурсия и ошибки

* **Запрет рекурсии.** В потоках-исполнителях выставлен TLS-флаг `srpc_disable_rpc_recursion`, поэтому исполнитель из обработчика не может сам сделать RPC-вызов: запрос не отправляется, код потока — `ERECURSIVE`.
* **Проверка в диспетчере.** Перед вызовом сравниваются адреса `&name` и `&sRPCFN(name)`. Их совпадение означает, что процесс попал в реестр без локальной реализации, и заглушка вызвала бы саму себя. Такой вызов не выполняется, а слот остаётся без ответа до таймаута.
* **Собственные коды.** `libsrpc` расширяет системный `errno` кодами после `MAX_ERRNO` (4095):

| Код | Значение | Смысл |
|---|---|---|
| `ELIBNOINIT` | 4096 | Библиотека не инициализирована |
| `ESHMNOINIT` | 4097 | Пул не подключён |
| `ERPCDISABLE` | 4098 | RPC выключен: нет связи с демоном |
| `ENOREGFUN` | 4099 | У функции нет исполнителей |
| `ERECURSIVE` | 4100 | RPC из потока-исполнителя запрещён |
| `ECANCELLED` | 4101 | Исполнитель отключился, не взяв запрос |
| `ENOTAVAILABLE` | 4102 | Нет доступного исполнителя или слота |
| `ERPCWAITIMEDOUT` | 4103 | Ответ не пришёл за таймаут |
| `ENOTFOUND` | 4104 | Блок не принадлежит исполнителю (удержание) |
| `EPROCDESTROYED` | 4105 | Исполнитель уже отключён (удержание) |
| `EINVALREQUEST` | 4106 | Нет пригодного последнего запроса (удержание) |
| `EINVALRESPONSE` | 4107 | Нет пригодного слота ответа (удержание) |

* **Где лежат коды.** Код ошибки потока хранится в TLS-переменной. Обёртка сбрасывает её в начале вызова и записывает причину, если запрос не удалось отправить. Читается через `libsrpc_errno_get()`, расшифровывается `libsrpc_strerror()`. Судьба отправленного запроса — в `rc` его слота, и её возвращает `libsrpc_lastreq_get()`. Таймаут и отмена в код потока не попадают.

## 🔄 Жизненный цикл RPC-вызова

1. **Инициализация.**
   * Приложение загружает `libsrpc.so`, выполняется конструктор с приоритетом 101.
   * Конструктор получает оригиналы `malloc`/`calloc`/`realloc`/`free` через `dlsym(RTLD_NEXT)`. По `program_invocation_name` он проверяет, не является ли процесс самим демоном. Если нет, поднимает демона (проигравший гонку `bind()` демон молча завершится) и запускает управляющий поток `unix_client`.
   * Поток подключается к сокету демона, отправляет битовую карту своих функций, получает FD пула и отображает его по фиксированному адресу.
   * Поток находит свой `libsrpc_proc_t` и `proc_uid`, запускает потоки-исполнители по числу доступных CPU, выставляет статус `RUN` и разрешает RPC. Конструктор всё это время ждёт и возвращает управление, когда процесс готов.

2. **Вызов (вызывающая сторона).**
   * Приложение вызывает `log_write("Hello")`. Символ разрешён в сгенерированную заглушку `librpcimp_log_write`.
   * Заглушка читает `num_all` из реестра. Если исполнителей нет, вызов сразу завершается с `ENOREGFUN`.
   * Берётся кэшированный или выделяется новый `libsrpc_request_t` (`libsrpc_shmem_malloc_type(..., LIBSRPC_SHMDT_REQUEST)`).
   * Аргументы копируются в `req->buf`, размечаются слоты ответов.
   * Для каждого выбранного исполнителя заполняется `resp->hp_proc`, и запрос кладётся в его MPMC-очередь. Если у исполнителя есть спящие потоки, делается `sem_post` на семафоре процесса.
   * Вызывающий поток засыпает на `req->sem_wakeup`.

3. **Обработка (поток-исполнитель).**
   * Поток-исполнитель, привязанный к своему ядру, забирает запрос из очереди: либо во время короткого активного ожидания, либо проснувшись на семафоре процесса.
   * Публикует Hazard Pointer `thread->hp_req` и повторно проверяет сигнатуру запроса.
   * Находит свой слот по `hp_proc`, раскладывает аргументы и вызывает настоящую `log_write()`.
   * Пишет результат в слот: `LOCK` → данные → `READY`.

4. **Завершение.**
   * Исполнитель делает `sem_post` на `req->sem_wakeup` и снимает Hazard Pointer.
   * Вызывающий просыпается и пересчитывает готовые слоты. Когда собраны все, обёртка возвращает результат слота 0. Остальные доступны через `libsrpc_lastreq_num()` / `libsrpc_lastreq_get()`.
   * Блок запроса остаётся в кэше потока для следующего вызова.

## 💥 Отказы и восстановление

* **Процесс умер посреди операции аллокатора.** Следующий захват мьютекса пула получает `EOWNERDEAD` и откатывает незавершённую операцию по BUL. Данные приложения внутри блоков не откатываются: структуры, которые приложение держит в пуле, оно защищает само, например robust-мьютексом с обработкой `EOWNERDEAD`.
* **Умер исполнитель.** Демон видит обрыв сокета и вызывает `libsrpc_proc_destroy()`:
  * процесс снимается из реестра, его дескриптор инвалидируется;
  * запросы, которые исполнитель не успел взять из очереди, получают `-ECANCELLED`, а вызывающие будятся;
  * запрос, который исполнитель уже обрабатывал, останется без ответа, и вызывающий получит `-ERPCWAITIMEDOUT` по таймауту;
  * блоки процесса разбираются обходом `tlsf_free_uid_blocks(pool, proc_uid, ...)`. Пользовательские освобождаются сразу, если их UID никто не удерживает, иначе откладываются в список GC. Блоки запросов гасятся и помечаются `dc`, дескриптор процесса освобождается через `libsrpc_shmem_free_dc()`.
* **Умер вызывающий.** Его блоки запросов гасятся и уходят к GC. Если сигнатура погашена до того, как исполнитель взял запрос, функция не вызывается. Если во время обработки — функция отработает, но результат не будет записан. GC освободит блок, когда Hazard Pointer исполнителя будет снят.
* **Умер держатель удержания.** Проверка удержаний смотрит только запросы живых процессов, а блок запроса потока освобождается при завершении потока. Поэтому удержание пропадает вместе с держателем, и отложенные блоки уходят в пул на ближайшем проходе GC. Забытый `unlock` в упавшем процессе не превращается в вечную утечку.
* **Исполнитель завис.** Вызывающий получает `-ERPCWAITIMEDOUT` по таймауту. Блок с просроченным слотом на следующем вызове заменяется новым, старый уходит к GC.
* **Умер демон.** Клиенты видят обрыв сокета: RPC в них выключается (`rpc_enable = false`), потоки-исполнители останавливаются. Переподключения нет. Отображение старого пула в процессах остаётся, но новые процессы поднимут новый демон с новым пулом и с уже работающими не встретятся. Демон — единая точка отказа.

## ⚙ Особенности реализации

* **Анонимная память (memfd).** Пул создаётся через `memfd_create`, а не `shm_open`. Он не виден в `/dev/shm`, и после последней ссылки на дескриптор ничего не остаётся: ручная чистка после падений не нужна.
* **Фиксированный базовый адрес.** Внутри пула лежат **абсолютные** указатели, поэтому все процессы отображают его по `SHMEM_BASE_VADR` (по умолчанию `0x200000000000`) с `MAP_FIXED_NOREPLACE`. Если адрес уже занят, отображение честно не создаётся, а не перезаписывает чужой регион.
* **Защита от fork.** Для пула вызывается `madvise(..., MADV_DONTFORK)`: дочерний процесс пул не наследует и не может случайно испортить метаданные аллокатора. Пользоваться RPC и пулом после `fork()` потомок тоже не может.
* **Многоядерность.** Потоки-исполнители создаются по числу разрешённых CPU и привязываются к ядрам через `pthread_attr_setaffinity_np`, что уменьшает переключения контекста и миграцию кэша.
* **Изоляция сборок через BUILD_TS.** Метка времени конфигурации вкомпилируется только в `libsrpc.so` и входит в имя демона, имя сокета, сигнатуру пула и сигнатуру регистрационного сообщения. Фактически это автоматическая версия ABI: процессы, загрузившие разные сборки библиотеки, друг друга не видят. Приложения метку не содержат. Их пересборка нужна при изменении `RPC_LIST`, потому что из него берутся прототипы и `libsrpc_funid_<name>`.
* **Параметры сборки.** Размер пула (`SHMEM_SIZE_KB`), базовый адрес (`SHMEM_BASE_VADR`), ёмкость очереди (`MPMCQ_DEGREE`), уровень сообщений (`DBG_LVL`) и отключение подмены аллокатора (`DISABLE_ALLOC`) задаются переменными CMake и попадают в код как `-D`-определения.
* **Строгие флаги.** Аллокатор собирается с `-Wall -Wextra -Werror -Wformat`, библиотека — с `-Wall -Wextra -Werror -Wconversion -Wshadow`. Неиспользуемые параметры помечаются `__attribute__((unused))`.
* **Привязка к x86_64.** Активное ожидание использует `__builtin_ia32_pause`, библиотека собирается с `-mrdrnd`. На других архитектурах код без доработки не соберётся.

## ⚠️ Известные ограничения

* **Таймаут считается от последнего ответа.** При рассылке нескольким исполнителям каждый пришедший ответ перезапускает интервал. В худшем случае общее ожидание приближается к числу исполнителей, умноженному на таймаут.
* **Неотправленный вызов может вернуть старое значение.** Если запрос не удалось отправить (`ERPCDISABLE`, `ERECURSIVE`, `ENOTAVAILABLE`), обёртка читает слот 0 переиспользуемого блока. В нём может остаться результат предыдущего вызова этого потока, и `libsrpc_lastreq_get(0)` тоже вернёт для него `0`. У функций с возвращаемым значением код причины при этом иногда заменяется на `ETIMEDOUT`. Надёжный признак успеха — `libsrpc_errno_get() == 0` **и** `0` в нужном слоте.
* **Коды ошибок функций памяти.** В код потока попадают `TLSF_ERR_*`, чьи номера совпадают с системными `errno`. `libsrpc_strerror()` расшифрует их неверно, нужен `tlsf_strerror()`.
* **Права клиентов не проверяются.** Из `SO_PEERCRED` берётся только PID. Любой процесс, подключившийся к абстрактному сокету с правильной сигнатурой, получает FD всего пула на чтение и запись.
* **Демон — единая точка отказа.** Переподключения к новому демону нет (см. «Отказы и восстановление»).
* **`libsrpc_fnreg_num_get()` без пула.** Функция не проверяет, подключён ли пул. Если подключение к демону не удалось, вызов обращается к несуществующей памяти.
* **Цена активного ожидания.** Каждый процесс держит потоки-исполнители по числу CPU, и после каждого запроса они какое-то время крутятся перед сном.
* **Фиксированный пул.** Размер пула задаётся при сборке и не растёт. Число одновременно подключённых процессов ограничено 16-битным `proc_uid`.
