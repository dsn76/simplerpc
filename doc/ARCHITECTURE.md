# Архитектура simplerpc

Документ описывает внутреннее устройство, компоненты и механизмы взаимодействия библиотеки `libsrpc`.

## 🏗 Общая концепция

**simplerpc** — это прозрачный RPC-фреймворк, работающий поверх разделяемой памяти (Shared Memory). В отличие от классических RPC-систем, использующих сериализацию в поток байтов (Protobuf, JSON) и передачу через сеть, `simplerpc` передает указатели на данные внутри общего сегмента памяти, что обеспечивает экстремально низкую задержку (low latency).

### Ключевые принципы
1. **Zero-Conf Daemon:** Фоновый процесс-координатор запускается автоматически при загрузке библиотеки в память любого приложения.
2. **Memory-Centric:** Все данные и очереди сообщений размещаются в разделяемой памяти, управляемой аллокатором TLSF.
3. **Transparent IPC:** Подмена стандартных функций (`malloc`, `free`) позволяет существующему коду работать с разделяемой памятью без изменений.

## 🧩 Основные компоненты

### 1. Guard Daemon (Фоновый демон)
Координирующий процесс, который управляет жизненным циклом RPC-сервера и пулом памяти.
* **Запуск:** Реализован через функцию `spawn_daemon()`. Демон создается с помощью двойного `fork()` и `setsid()`.
* **Embedded Loader:** Исполняемый файл демона не лежит на диске. Он встроен в саму библиотеку `libsrpc.so` в виде C-массива (через `xxd`), записывается во временный `memfd` в оперативной памяти и запускается через `fexecve()`. Это обеспечивает безопасность и независимость от файловой системы.
* **Роль:** Создает абстрактный Unix-сокет, выделяет общую память и раздает файловые дескрипторы памяти подключающимся клиентам.

### 2. Транспортный уровень (Unix Sockets & SCM_RIGHTS)
Используется исключительно для сигнального взаимодействия и установления соединения.
* **Клиент-Сервер:** При подключении клиента демон передает ему файловый дескриптор (FD) разделяемой памяти через механизм `SCM_RIGHTS` (ancillary data).
* **mmap:** Получив FD, клиент выполняет `mmap()` того же региона памяти, что и демон, по заранее согласованному виртуальному адресу (`SHMEM_BASE_VADR`). Это гарантирует, что указатели, созданные в одном процессе, будут валидны в другом.

### 3. Управление памятью (TLSF Shared Memory)
* **TLSF (Two-Level Segregated Fit):** Детерминированный аллокатор памяти, интегрированный в проект через git-подмодуль. Обеспечивает быстрое выделение блоков в O(1).
* **Robust Mutexes:** Доступ к метаданным памяти защищен мьютексами POSIX с атрибутом `PTHREAD_MUTEX_ROBUST`. Если процесс, владеющий мьютексом, упадет (segfault), мьютекс не останется заблокированным навсегда, а аллокатор TLSF попытается восстановить консистентность пула (`tlsf_bul_recover`).
* **Allocator Hijacking:** Библиотека перехватывает стандартные функции `malloc`, `calloc`, `realloc` и `free` через `dlsym(RTLD_NEXT)`. С помощью `Thread Local Storage` (TLS) и атомарных флагов библиотека позволяет потоку переключаться между системным аллокатором и аллокатором разделяемой памяти "на лету".

### 4. Механизм RPC и Макросы (X-Macro)
Для исключения boilerplate-кода используется препроцессор C.
* **RPC_LIST:** Макрос, содержащий список всех регистрируемых функций.
* **Генерация оберток:** На этапе компиляции генерируются функции-заглушки (`sRPCFN`), которые сериализуют аргументы в буфер запроса (`srpc_req_t`) и помещают его в MPMC-очередь.
* **Диспетчеризация:** Каждая функция получает уникальный ID (`sRPCFNID_`). На стороне воркера макросы `M_DECL`, `M_EXTRACT` автоматически десериализуют буфер обратно в переменные стека и вызывают оригинальную функцию.

### 5. Синхронизация и Очереди (Futex & MPMC)
* **MPMC Queue:** Lock-free (без блокировок) очереди типа Multi-Producer Multi-Consumer, размещенные в разделяемой памяти. Используются для передачи задач от клиента к воркерам сервера.
* **POSIX Semaphores:** Семафоры `sem_wait`/`sem_post` используются для усыпления и пробуждения потоков-воркеров при отсутствии задач в очередях (экономия CPU).
* **Job Futex:** Пользовательская реализация фьютексов для точечного уведомления клиента о том, что конкретный RPC-запрос выполнен и результат готов к чтению.

## 🔄 Жизненный цикл RPC-вызова

1. **Инициализация:**
   * Приложение загружает `libsrpc.so`.
   * Конструктор библиотеки проверяет, не является ли текущий процесс Демоном. Если нет — форкает Демона.
   * Клиент подключается к Unix-сокету Демона, получает FD памяти, делает `mmap` и регистрирует свои потоки-воркеры.

2. **Вызов функции (Client Side):**
   * Пользователь вызывает `log_write("Hello")`.
   * Макрос перехватывает вызов, выделяет `srpc_req_t` в Shared Memory через `libsrpc_shmem_malloc`.
   * Аргументы копируются в `req->buf`.
   * Запрос атомарно помещается в MPMC-очередь целевого процесса.
   * Поток клиента блокируется на `job_futex`, ожидая ответа.

3. **Обработка (Server Side / Worker Thread):**
   * Фоновый поток воркера (запущенный на отдельном ядре CPU) просыпается на семафоре.
   * Извлекает `srpc_req_t` из очереди.
   * Десериализует аргументы из буфера.
   * Вызывает реальную реализацию `log_write()`.
   * Копирует возвращаемое значение (если есть) в `req->buf`.

4. **Завершение:**
   * Воркер инкрементирует счетчики и вызывает `job_futex_worker_done()`.
   * Клиент просыпается, читает результат, освобождает `srpc_req_t` через `libsrpc_shmem_free()`.

## 📊 Диаграмма взаимодействия

```text
+-------------------+                       +-------------------+
|   Process A       |                       |   Process B       |
|  (RPC Client)     |                       |  (RPC Server)     |
+-------------------+                       +-------------------+
          |                                           |
          |  1. log_write("Msg")                      |
          v                                           v
+-------------------+       Shared Memory     +-------------------+
| RPC Wrapper       | <--- (mmap TLSF) -----> | Worker Thread     |
| - Serialize Args  |       [MPMC Queue]      | - Deserialize     |
| - Alloc Request   | ======================> | - Call Function   |
| - Futex Wait      |                         | - Write Result    |
+-------------------+                         +-------------------+
          ^                                           |
          |                                           |
          +-------------------------------------------+
                  2. Futex Wakeup / Result Read
```

## ⚙ Особенности реализации

* **Анонимная память (memfd):** Вместо `shm_open` используется `memfd_create`, что позволяет создавать объекты разделяемой памяти, которые не видны в файловой системе (`/dev/shm`), повышая безопасность и упрощая очистку ресурсов.
* **Защита от Fork:** Для региона разделяемой памяти вызывается `madvise(..., MADV_DONTFORK)`, чтобы предотвратить наследование памяти дочерними процессами и нарушение работы TLSF-аллокатора.
* **Многоядерность:** Потоки-воркеры привязываются к ядрам CPU (`pthread_start_all_cpu`), что минимизирует накладные расходы на переключение контекста и миграцию кэша.
